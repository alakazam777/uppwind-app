# Releasing the companion

A release is `uppwind-companion.exe` (and, once switched on, `uppwind-companion-macos.dmg`) and their SHA-256, nothing else. The Uppwind Link plugins are **inside** the companion (it installs them itself), built from the same tag with the same flags, so they are not a separate download; the .dmg also holds the signed `Uppwind Link.vst3`. Never publish a `.pdb`, the `.d` files or a `target/` folder: they hold the build machine's paths.

## The workflows (GitHub Actions)

- `.github/workflows/ci.yml`, on every push and pull request: on Windows, the plugins' tests, the plugins built and bundled, the companion's tests with that bundle inside (`cargo test --release --locked`, the registry test included: it writes `HKCU\Software\UppwindLinkTest` on the runner and deletes it), the companion built and checked to install exactly those plugin bytes (into a folder of the runner, `--plugins-dir`) and remove them, the Python tests, `third_party_notices.py --check`; the same on macOS (arm64, the bundle signed ad hoc, the installed copy checked with `codesign --verify`; no Developer ID); `cargo audit` and `cargo deny` for the companion and for the plugins (rules in `deny.toml`); `gitleaks` on the files and on the git history.
- `.github/workflows/release.yml`, on a tag `v*` (it must match `version` in `companion/Cargo.toml`): steps 3 to 5 and 7 below on a `windows-2025` runner, then a GitHub release with `uppwind-companion.exe` and `SHA256SUMS` only, and an artifact attestation. To release: bump the version in `companion/Cargo.toml` (and `Cargo.lock`), wait for `ci` to be green on `main`, then `git tag v<version>` and `git push origin v<version>`.
- `.github/workflows/macos-build.yml` (called by the two below), on a `macos-latest` runner: the tests (plugins, companion), `third_party_notices.py --check`, a keychain made for the job with the *Developer ID Application* certificate (deleted at its end, whatever happens), then `dev/build-macos.sh` with `UWL_RELEASE=1` (`--locked`, the runner's paths remapped): the plugins first, universal (arm64 + x86_64), their bundles signed with the Developer ID (hardened runtime, Apple's timestamp), THEN the universal companion with that signed `Uppwind Link.vst3` inside; `release_check.py` on both binaries; the companion signed (hardened runtime, timestamp, identifier `com.uppwind.link.companion`, no entitlements) and checked to install exactly the signed bundle (`diff -r`, `codesign --verify --deep --strict`); `uppwind-companion-macos.dmg` with the companion, `Uppwind Link.vst3` (so that notarization covers it, and a user can drag it into `~/Library/Audio/Plug-Ins/VST3`), the README, the licences and both notices; the .dmg signed, notarized (`notarytool`, its log printed) and stapled, then checked like a user would get it (`stapler validate`, `spctl`, both signatures in the mounted .dmg, the companion of the .dmg installing its bundle). Secrets: `MACOS_CERT_P12_BASE64`, `MACOS_CERT_PASSWORD`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD`.
- `.github/workflows/macos-preview.yml`, started by hand (`gh workflow run macos-preview.yml`): that .dmg as a workflow artifact only, no release.
- macOS in a release: only when the repository variable `MACOS_RELEASE` is `1` (`gh variable set MACOS_RELEASE --body 1`); then `release.yml` adds `uppwind-companion-macos.dmg` to the release and to `SHA256SUMS`. Off by default: a tag ships Windows only.

Both pin every action by its commit SHA and every tool by its version (gitleaks by its SHA-256 too) and use the same Rust version (`RUST_VERSION`); update them together.

## Before every release

1. **Dependencies** (online): `cargo audit --deny warnings --file companion/Cargo.lock` (two advisories of Linux-only crates ignored, see `ci.yml`), `cargo audit --deny warnings --file plugin/Cargo.lock`, and `cargo deny --manifest-path <companion/Cargo.toml, then plugin/Cargo.toml> --config deny.toml check advisories bans licenses sources` must pass (the `ci` workflow runs them all). Then `cargo fetch --locked` for both manifests and `python -I dev/third_party_notices.py --check`: after any dependency change, rerun it without `--check` and commit `THIRD-PARTY-NOTICES.txt` and `plugin/THIRD-PARTY-NOTICES.txt` (each lists the Windows crates, then the macOS-only ones).
2. **Secrets and personal data** in the sources (and in the git history of this repository): `gitleaks detect` must find nothing. Look at every new file before the commit that adds it.
3. **Tests**: the commands of *Build from source* in the README, all green.
4. **Build from a clean checkout of the release tag**, ideally in CI (a GitHub Actions Windows runner), never from a working copy with stray files. The plugins first, with the same flags as the companion, then their bundle, then the companion with that bundle inside:

   ```
   set REMAP=target.x86_64-pc-windows-msvc.rustflags=['--remap-path-prefix=<CARGO_HOME>=/cargo', '--remap-path-prefix=<checkout folder>=/src']
   cargo --config "%REMAP%" build --release --locked --manifest-path plugin/Cargo.toml
   plugin\target\release\uwl-bundle.exe --out plugin\target\release\bundled
   set UWL_PLUGIN_BUNDLE=<checkout folder>\plugin\target\release\bundled\Uppwind Link.vst3
   cargo --config "%REMAP%" build --release --locked --manifest-path companion/Cargo.toml
   ```

   Run it from the repository folder, so that cargo reads `.cargo/config.toml` (the static C runtime, `/DEPENDENTLOADFLAG:0x800`, `/Brepro`: for the plugins' DLL too); `--config` adds the path remapping to those flags. Don't set `RUSTFLAGS`: it would replace them all. `UWL_PLUGIN_BUNDLE` must be an absolute path; `companion/build.rs` embeds every file of that bundle and stops on anything but the expected layout (the DLL alone on Windows). Write down the Rust version (`rustc -V`) and the Visual Studio build tools and Windows SDK versions with the release.
5. **Check the plugins and the program**: `python -I dev/release_check.py "plugin/target/release/bundled/Uppwind Link.vst3/Contents/x86_64-win/Uppwind Link.vst3" companion/target/release/uppwind-companion.exe` must print `ok` (no user, cargo or drive paths, in the DLL nor in the exe that carries it; DLLs from System32 only; no separate C runtime; reproducible builds). Then the program must install exactly that DLL: `uppwind-companion.exe --install-plugins --plugins-dir <an empty folder>` and compare the SHA-256 of the installed `Uppwind Link.vst3\Contents\x86_64-win\Uppwind Link.vst3` with the checked one (`--install-plugins --dry-run` also prints the SHA-256 of the files it carries). Build twice from clean checkouts at the **same folder path** (each into fresh `target` folders): the two SHA-256 must be equal, for the DLL and for the exe. The folder path is part of the build: it sits in the `--remap-path-prefix` flags, which cargo hashes into every crate's symbol names, so the same sources built from another folder give another (equally valid) exe. Write the folder path down with the release (in GitHub Actions it is always `D:\a\uppwind-app\uppwind-app`), so anyone can rebuild it byte for byte.

   macOS (`macos-build.yml` does it): `UWL_RELEASE=1 UWL_NO_ADHOC=1 UWL_PLUGIN_SIGN_IDENTITY=<Developer ID Application identity> UWL_SIGN_KEYCHAIN=<keychain> sh dev/build-macos.sh <folder>` builds and signs the plugins, then the companion that embeds them; `release_check.py` on `uppwind-companion` and on `Uppwind Link.vst3/Contents/MacOS/Uppwind Link`. The plugin's install name is neutral (`plugin/plugins/build.rs`), so the dylib holds no build path either. A plugin bundle is signed before the companion embeds it: re-signing it afterwards would make the embedded copy differ from the published one.
6. **Sign it** when a certificate is available (SignPath Foundation is free for open-source projects; Azure Trusted Signing; an OV certificate), then check the signature.
7. **Publish** the exe and a `SHA256SUMS` file on the GitHub release; if the build runs in GitHub Actions, add an artifact attestation (`actions/attest-build-provenance`) so that `gh attestation verify` works.

## The repository itself

- Commit with the GitHub *noreply* address only, set in this repository (`git config user.email <id>+<login>@users.noreply.github.com`), never globally. Before a push, `git log --format="%an <%ae> | %cn <%ce>"` must show only that address.
- On GitHub: *Keep my email addresses private* and *Block command line pushes that expose my email*, two-factor authentication, secret scanning with push protection, Dependabot alerts, private vulnerability reporting (SECURITY.md relies on it).
- CI workflows (`.github/workflows/`, see above): actions pinned by commit SHA, `permissions: contents: read` by default, `contents: write`, `id-token: write` and `attestations: write` only in the job that publishes the release.
- Outside contributions: decide before the first pull request how they are licensed (a DCO, "inbound = outbound", is the simplest), or relicensing later needs every contributor's consent.
