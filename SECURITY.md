# Security policy

## Reporting a vulnerability

Please **do not open a public issue** for a security problem. Report it privately with GitHub: open this repository's **Security** tab, then **Report a vulnerability**. Include what you found, how to reproduce it, and which version (`uppwind-companion --help` prints it) and which system (Windows build, or macOS version) you used.

You will get an answer as soon as possible. A fix is released first, then the report is published with credit to you, unless you prefer otherwise.

## Scope

In scope: the Uppwind Link companion (`companion/`, Windows and macOS), the Uppwind Link plugins (`plugin/`), the scripts for Ableton Live and FL Studio (`ableton/UppwindLink/`, `fl-studio/`, `shared/`) and the protocols between them and Uppwind Studio. Examples: a page other than the studio's that can drive the companion; a way around the pairing code or the plugins' secret; a way to make the companion show, click or capture anything other than a DAW's plugin windows and the DAW's own sound; anything that reads or writes files, or runs a program; a way to make the companion's copy with administrator rights (Windows: the plugins' folder only) write, remove or run anything else; a crash caused by a message.

Since 19 Nov 2026 (Windows) the companion can also **host VST 3 plugins itself**, without a DAW (`companion/src/host.rs`, `plugin/host`): when remote control is on, the studio can make it load a VST 3 plugin, one plugin per child process. What the studio can ask is narrow on purpose, and any way around it is in scope: it names a plugin only by the class id that the companion's own scan found in the standard VST 3 folders (`Common Files\VST3`, `%LOCALAPPDATA%\Programs\Common\VST3`), never a path; a plugin's saved settings are only ever read back from a file the companion wrote itself (`plugin-states\<sha256>.bin`, checked against its name), never from bytes a project carries; the plugin's own window can be shown on the desktop, or opened hidden so that the studio films it and sends it gestures (clicks, the wheel, typing into the plugin's own fields; never a keyboard shortcut: Ctrl, Alt, Meta and the F keys are refused), under the same rules as a DAW's plugin windows: only while remote control is on, and when it goes off (by you, or after 10 minutes without the studio) the companion closes every hosted plugin's window at once and stops listing them for capture. Every plugin runs in its own child process, tied to the companion (a Windows job object): if the companion stops or crashes, they stop too. At most 16 plugins are hosted at once, counted before any of them starts. Error messages sent to the studio never carry a file path (the full message stays in the companion's log). Since 0.4.13 the studio can also read a hosted plugin's parameter names and values, set one (0..1, by index) and follow those its editor moves (`params`, `param-set`, `param-watch`, `param-changes`), only while remote control is on: nothing a plugin's own editor could not do. On macOS (0.4.13) the same rules hold, with these differences: plugins are loaded by `uppwind-link-host`, a small program that ships next to the companion and that the companion starts (since 0.4.15 it also checks, itself, that a module comes from the VST 3 folders); it is the only program signed with the `disable-library-validation` entitlement (needed to load other makers' plugins, as in every DAW), while the companion, which holds the pairing code and arming, keeps the hardened runtime with no entitlement, so it never loads another maker's code itself. This is not a sandbox: a plugin runs as you, like in any DAW (before 0.4.15, macOS let the helper, a child of the companion, use the companion's Screen Recording and Accessibility permissions; since 0.4.15 it drops them, see below); plugins come from `/Library/Audio/Plug-Ins/VST3` and `~/Library/Audio/Plug-Ins/VST3`; there is no job object, so a plugin process stops by itself at most 1 second after the companion's end (0.4.15; 5 seconds before); keys from the studio are checked when they are delivered, on the plugin process's main thread, and dropped while the plugin shows a modal dialog or a sheet, so typing never reaches a file dialog the studio cannot see; only Shift travels with them. Bugs inside a third-party plugin itself are for its maker, unless the companion is what lets a web page reach them. Since step 3 (19 Nov 2026) the studio can also have a hosted **effect** applied to a sound, offline: the studio may send that sound as binary. Only while remote control is on, only inside a render the companion opened (`render-begin`: one at a time per connection, 10 minutes at most), in order, never past the announced length, each piece under the connection's 16 KB message limit. The sound and its result are files the companion names in its own folder (`jobs\`), deleted when the render ends and at start-up; all renders together may take 2 GiB at most, reserved when each render opens. Since step 3b (19 Nov 2026) a hosted effect can also run **live**: the studio sends a track's sound in small packets (`UWF1`, 512 frames at most, each stamped with its position) and gets the effect's output back. Only while remote control is on, only on a stream the studio opened for that effect (`fx-live`, streams 9..16), and never faster than the sound itself (a quarter more, half a second ahead at most: anything beyond is dropped). These packets go to the effect's child process only, in memory, and are never written to disk. The studio also tells each live effect where the song is (`tempo` with the effect's `id`, `from`, `offset`, `playing`): three numbers, bounded, passed to that child only; they change nothing but the position the plugin reads. Any other binary closes the connection as before. Since 0.4.14: at most 64 hosting requests run at once (8 for one hosted plugin), beyond that the studio gets « busy » at once; a child drops any line from the companion longer than 16 KB as it reads it, never holding it; a render only reads and writes the two files the companion named in its `jobs` folder; on Windows a child removes the current folder from the DLL search before loading a module, which it loads by absolute path only; a scan stops by itself after 40 seconds; on macOS a press from the studio outside the editor (on its hidden title bar) is dropped; and the `UWL_HOST_*` test variables are read only by development builds. Since 0.4.15: when remote control is off and no studio has been connected for a minute (after the 10-minute auto-off, for instance), the companion unloads every hosted plugin, not only its window; a studio that comes back reopens them, as after a restart of the companion; a plugin whose settings changed since the studio last saved them (or, never saved, since it opened) is not unloaded: it stays loaded with its window closed, neither filmed nor driven, until a studio comes back and saves them, and is asked again every minute; and the temporary settings files a killed child may leave (`plugin-states\.tmp-*`) are removed when that child ends, and at start-up once they are ten minutes old.

Since 0.4.15 (24 Nov 2026, after the security audit of 23 Nov): on a Mac, the studio types nothing into a DAW's plugin window (Live, as already for Logic Pro): a key posted to the DAW could reach its own shortcuts or a dialog a click just opened (typing into a plugin hosted by Uppwind Link still works, checked by its own process when each key is delivered); a press or a wheel notch goes only where the watched plugin window (or one of its menus) is the DAW's topmost window under the pointer; an open menu (Live's own, or one a plugin opens in Live, neither of which is filmed) never counts, so in Live on a Mac no menu can be driven from the studio, and a press on one is refused (only presses and wheel notches are checked, not the release). `uppwind-link-host` itself loads a module only from the two VST 3 folders (the bundle's path resolved, links followed; the home folder read from the account database, not from `HOME`), whoever starts it, and restarts itself in place at once without the companion's responsibility (`posix_spawn`, `POSIX_SPAWN_SETEXEC`, `responsibility_spawnattrs_setdisclaim`): a hosted plugin no longer gets the companion's Screen Recording and Accessibility permissions (measured on macOS 26.6: `AXIsProcessTrusted` 1 before, 0 after, same pid). The hosted plugins' data (scan cache, saved settings, renders) live in `~/Library/Application Support/Uppwind Link` (0700), no longer in your home folder. While a hosted plugin's menu is open, only arrows, Return and Escape reach it, and keys left over when it closes are dropped, so they never land in a dialog the menu opens; the hidden title bar is protected on that path too. Through the Live script's link, ADD, REMOVE and PARAM_SET need remote control (the studio is told at once, in the link's own protocol), at most 64 link chunks a second for all the studio's connections together; BIND (which may add a helper track with Uppwind Link Notes), SET and TEMPO stay available without it; BIND has its own lower limit, 48 every 10 seconds for all connections together (refused ones get the link's own error at once). The HTTP handshake must finish within 5 s in all; refused connections (refused handshakes, connections over the limit, failed accepts) write at most 10 lines a minute to the log together; a handshake that finishes releases its watchdog at once. When all 16 places of the studio's port (or of the plugins' port) are taken, the oldest connection that has not yet proved the pairing code (the plugins' secret), if it is at least 1 second old, is closed to let the new one in; a paired connection is never closed this way. Windows: keys from the studio to a DAW's plugin window never carry Alt (except AltGr, Ctrl+Alt with a printable character, for `@ # { }` on some layouts), and Alt, F10 and the menu key are never sent; when no window of the plugin was chosen for the keyboard (none has the focus, none was clicked: the key would go to the plugin's view at the centre, or to the DAW's own frame), Ctrl, Alt and the F keys are refused too (0.4.16); Ctrl+letter and F keys still reach a part of the plugin that has the focus or was clicked, and once the plugin was clicked, a plugin that does not use such a key (Ctrl+letter, an F key) may still pass it on to the DAW: the companion cannot tell; the exe and the plugin DLL are built with Control Flow Guard and the exe carries a manifest (`asInvoker`, PerMonitorV2), both checked by `dev/release_check.py` (0.4.16; Rust's prebuilt standard library is not instrumented, so its own indirect calls are not checked, and only the x86_64 build has these options); the cleanup command runs `PING.EXE` by its full path; the Discord pipe is opened with `SECURITY_IDENTIFICATION`; *Update automatically* is not offered until updates are signed, and a box ticked by an older version is cleared. The studio no longer sends a pairing code in clear to anything (the fallback for 0.1 companions is gone), and a project opened in the studio asks before it opens a hosted plugin that this browser has not opened before. Known limits: a program on your computer that reconnects about 50 times a second can still keep the studio's (or the plugins') port full: a connection younger than 1 second is never closed for another, so such a program keeps every place, and the studio only gets in by chance (measured 0/15 on 24 Nov); a program you run yourself is outside this policy anyway; any script running on the studio's website can read the pairing code (it is stored in that site's local storage).

Since 0.4.16 (audit of 23 Nov 2026, finding E2), **updates are signed**: before it downloads an update, the Windows companion checks a [minisign](https://jedisct1.github.io/minisign/) signature (Ed25519) of the release's `SHA256SUMS`, made with an Uppwind update key that is kept offline, never on GitHub nor on a build machine, and whose signed comment names that release's tag (`companion/src/update.rs`, `verify_signature`; the public keys are `UPDATE_KEYS` there, and `uppwind-companion.exe --update-keys` prints them). Any way to make a companion install, or even write to disk, a program that this signature does not cover is in scope: a parsing gap, a release that passes for another one, an older signed version served as a newer one, a path that skips the check. At most two keys are accepted at a time (the main one and a backup kept apart, for replacing a lost or stolen key: RELEASING.md, *The update keys*). Since 0.4.16 the companion also asks for the latest release by the repository's number (`API_LATEST`), never by an account name, and downloads each file at the address that answer gives for it, of one shape only (`asset_url`). Versions up to 0.4.15 check the SHA-256 only, without a signature.

Since FL Studio script 1.5.0 and Live script 1.4.0 (24 Nov 2026, audit finding M3), **the MIDI path to the DAW scripts is authenticated**. A loopMIDI port (or an IAC bus) is a shared bus: any program on the computer, and any web page you allowed *MIDI with SysEx*, can write to it. So each script has a **MIDI link code** (15 random bytes, shown as 24 characters), and obeys only a studio that proves it knows that code:
- **Where the code comes from.** When the companion installs or updates a script, it writes `uwl_secret.py` next to it (kept across updates) and gives the code to the studio it is paired with (`midicodes`, after pairing only). Without that file, Live's script draws a code once and keeps it in `~/.uppwind-link-midi.json` (0600); FL's script, which cannot write files, draws a new one each time FL starts, from the system's random source. If that Python has no system random source, the script has no code and obeys nothing over MIDI (a code drawn from the clock could be guessed): install the script with the companion. The script shows a code only for pasting: FL shows a code of this launch in its hint bar when a studio asks, and writes it once per launch in *View › Script output*; Live shows its kept code in its status bar when a studio asks, and writes only its id (`kid`) in `Log.txt`. A code from the companion is never shown or logged, only its id. The person pastes the code in the studio, which keeps it in this browser's local storage, by script.
- **How it is proved.** `HELLO` → `HELLO_ACK.auth {kid, n}` → `AUTH {n, p = HMAC-SHA256(code, "uwl-midi-studio|" n_script "|" n_studio)}` → `AUTH_ACK {p}` (the script proves it too). Then **every** command from the studio carries a counter and a 16-byte HMAC with the session key, checked on the exact bytes received: a command that is not signed, signed with another key, altered or replayed is refused (`ERROR auth`). Without a proof, a script accepts only `HELLO` (which no longer ends the current session) and `ERROR`; refusals are logged at most once every 10 s, and the text of an `ERROR` only when the session signed it. A new valid `AUTH` while a session is open changes the key without resetting the DAW: the links the studio binds again stay, the others are undone after 10 s. The studio connects again on `ERROR auth` only when it answers one of its own signed requests, at most after 5 s, then 10, 20… up to 60 s; and only one tab of the studio (a `navigator.locks` lock) talks to the script over MIDI. `uwl_secret.py` is written through a new file created private (0600 on a Mac) and renamed over the old one; backups of a script folder do not copy it. The companion reads the codes again at most every 10 s. Live's companion channel (UDP, 256-bit token) was already authenticated and is unchanged.
- **What it does not protect.** A program running under your account can read `uwl_secret.py`, `~/.uppwind-link-midi.json`, Live's log, or the studio's local storage, and then drive the script. Notes, pitch bend and CC 1, 7, 10, 11, 64 are plain MIDI messages, not SysEx: anyone can still play notes on the linked instruments through the port (in FL, those CCs reach the linked VSTs' "MIDI CC" parameters). The replies on `Uppwind Link Back` are neither signed after the handshake nor encrypted: any program can read them (project and track names, watched parameter values) or send the studio false ones, including a false `ERROR auth` that makes the studio connect again (bounded as above, and with no effect on the DAW). Flooding the port still works. On Windows no access control is set on `uwl_secret.py`: it has its folder's rights (under your profile, your account, SYSTEM and administrators; a Live User Library on another drive is often readable by every account on the computer). An older script (FL before 1.5.0, Live before 1.4.0) is still driven by the studio, which then says it is not protected.
- In FL, since 1.4.1, `PARAM_SET` only reaches the instrument the studio linked (`BIND`) or watches (`PARAM_WATCH`); in both scripts, at most 512 reply chunks wait to go out (a whole message is dropped beyond, never half of one).

Not in this repository, but welcome the same way: problems in the Uppwind Studio website. Out of scope: programs already running under your own account (they can read the pairing code like any of your files: see *Security model* in the README), and attacks that need administrator rights on your computer.

## Supported versions

Only the latest release gets security fixes.

## Before you share a log or a console output

The companion never writes the pairing code to its background log. Its console window shows the code once, so that you can copy it: remove any line starting with `UWC2-` (or `UWC-`, older companions) before you paste console output anywhere. Logs also contain the names of your plugins and tracks.
