# Security policy

## Reporting a vulnerability

Please **do not open a public issue** for a security problem. Report it privately with GitHub: open this repository's **Security** tab, then **Report a vulnerability**. Include what you found, how to reproduce it, and which version (`uppwind-companion --help` prints it) and which system (Windows build, or macOS version) you used.

You will get an answer as soon as possible. A fix is released first, then the report is published with credit to you, unless you prefer otherwise.

## Scope

In scope: the Uppwind Link companion (`companion/`, Windows and macOS), the Uppwind Link plugins (`plugin/`), the scripts for Ableton Live and FL Studio (`ableton/UppwindLink/`, `fl-studio/`, `shared/`) and the protocols between them and Uppwind Studio. Examples: a page other than the studio's that can drive the companion; a way around the pairing code or the plugins' secret; a way to make the companion show, click or capture anything other than a DAW's plugin windows and the DAW's own sound; anything that reads or writes files, or runs a program; a way to make the companion's copy with administrator rights (Windows: the plugins' folder only) write, remove or run anything else; a crash caused by a message.

Since 19 Nov 2026 (Windows) the companion can also **host VST 3 plugins itself**, without a DAW (`companion/src/host.rs`, `plugin/host`): when remote control is on, the studio can make it load a VST 3 plugin, one plugin per child process. What the studio can ask is narrow on purpose, and any way around it is in scope: it names a plugin only by the class id that the companion's own scan found in the standard VST 3 folders (`Common Files\VST3`, `%LOCALAPPDATA%\Programs\Common\VST3`), never a path; a plugin's saved settings are only ever read back from a file the companion wrote itself (`plugin-states\<sha256>.bin`, checked against its name), never from bytes a project carries; the plugin's own window can be shown on the desktop, or opened hidden so that the studio films it and sends it gestures (clicks, the wheel, typing into the plugin's own fields; never a keyboard shortcut: Ctrl, Alt, Meta and the F keys are refused), under the same rules as a DAW's plugin windows: only while remote control is on, and when it goes off (by you, or after 10 minutes without the studio) the companion closes every hosted plugin's window at once and stops listing them for capture. Every plugin runs in its own child process, tied to the companion (a Windows job object): if the companion stops or crashes, they stop too. At most 16 plugins are hosted at once, counted before any of them starts. Error messages sent to the studio never carry a file path (the full message stays in the companion's log). Since 0.4.13 the studio can also read a hosted plugin's parameter names and values, set one (0..1, by index) and follow those its editor moves (`params`, `param-set`, `param-watch`, `param-changes`), only while remote control is on: nothing a plugin's own editor could not do. On macOS (0.4.13) the same rules hold, with these differences: plugins are loaded by `uppwind-link-host`, a small program that ships next to the companion and that only the companion starts; it is the only program signed with the `disable-library-validation` entitlement (needed to load other makers' plugins, as in every DAW), while the companion, which holds the pairing code and arming, keeps the hardened runtime with no entitlement, so it never loads another maker's code itself. This is not a sandbox: a plugin runs as you, like in any DAW, and macOS most likely lets the helper, a child of the companion, use the companion's Screen Recording and Accessibility permissions; plugins come from `/Library/Audio/Plug-Ins/VST3` and `~/Library/Audio/Plug-Ins/VST3`; there is no job object, so a plugin process stops by itself at most 5 seconds after the companion's end; keys from the studio are checked when they are delivered, on the plugin process's main thread, and dropped while the plugin shows a modal dialog or a sheet, so typing never reaches a file dialog the studio cannot see; only Shift travels with them. Bugs inside a third-party plugin itself are for its maker, unless the companion is what lets a web page reach them. Since step 3 (19 Nov 2026) the studio can also have a hosted **effect** applied to a sound, offline: the studio may send that sound as binary. Only while remote control is on, only inside a render the companion opened (`render-begin`: one at a time per connection, 10 minutes at most), in order, never past the announced length, each piece under the connection's 16 KB message limit. The sound and its result are files the companion names in its own folder (`jobs\`), deleted when the render ends and at start-up; all renders together may take 2 GiB at most, reserved when each render opens. Since step 3b (19 Nov 2026) a hosted effect can also run **live**: the studio sends a track's sound in small packets (`UWF1`, 512 frames at most, each stamped with its position) and gets the effect's output back. Only while remote control is on, only on a stream the studio opened for that effect (`fx-live`, streams 9..16), and never faster than the sound itself (a quarter more, half a second ahead at most: anything beyond is dropped). These packets go to the effect's child process only, in memory, and are never written to disk. The studio also tells each live effect where the song is (`tempo` with the effect's `id`, `from`, `offset`, `playing`): three numbers, bounded, passed to that child only; they change nothing but the position the plugin reads. Any other binary closes the connection as before. Since 0.4.14: at most 64 hosting requests run at once (8 for one hosted plugin), beyond that the studio gets « busy » at once; a child drops any line from the companion longer than 16 KB as it reads it, never holding it; a render only reads and writes the two files the companion named in its `jobs` folder; on Windows a child removes the current folder from the DLL search before loading a module, which it loads by absolute path only; a scan stops by itself after 40 seconds; on macOS a press from the studio outside the editor (on its hidden title bar) is dropped; and the `UWL_HOST_*` test variables are read only by development builds.

Not in this repository, but welcome the same way: problems in the Uppwind Studio website. Out of scope: programs already running under your own account (they can read the pairing code like any of your files: see *Security model* in the README), and attacks that need administrator rights on your computer.

## Supported versions

Only the latest release gets security fixes.

## Before you share a log or a console output

The companion never writes the pairing code to its background log. Its console window shows the code once, so that you can copy it: remove any line starting with `UWC2-` (or `UWC-`, older companions) before you paste console output anywhere. Logs also contain the names of your plugins and tracks.
